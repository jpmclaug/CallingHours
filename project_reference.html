A working map of Calling Hours

Calling Hours turns a song search into a durable music-research record: lyrics, Gemini interpretation, provider intelligence, artist discovery, personal ratings, and exportable playlists meet in one web application.

End to end

How a song becomes a library entry

Searches are cached by normalized artist and title. Enrichment and analysis are added as available; missing external data does not prevent manual lyrics analysis.

1 · Find lyricsRead cache first; otherwise resolve through Genius and fall back to LRCLIB.
2 · EnrichFetch Last.fm tags and TheAudioDB details, concurrently where practical.
3 · Analyze or editReview or paste lyrics, choose a prompt/model, and request Gemini analysis.
4 · Keep and reusePersist the search and analysis for history, playlists, and discovery.
Persistence: Neon PostgreSQL is selected when configured; SQLite is the local default and fallback. Lyrics and analysis are stored in searches; provider data is cached with song and artist records.

Feature guide

Each entry covers the user workflow and implementation behavior, including database and provider dependencies.

Lyrics search and recovery

Search by artist and song. The handler checks the database first unless a refresh is requested. On a miss it resolves a Genius song and retrieves lyrics; if Genius lookup or page access fails, it queries LRCLIB. Canonical Genius artist/title values are retained when available. Search source and Genius URL are saved when known.

If neither provider returns lyrics, users can paste text into the editable workspace and continue to analysis. Equivalent artist/title spellings are normalized for lookup and upsert.

Lyrics workspace and Gemini analysis

Users can edit or supply lyrics, choose an exposed Gemini model, and run a saved prompt template. Templates interpolate {song}, {artist}, and {lyrics_text}. The resulting analysis, model name, and prompt name are saved with the matching song record.

The page exposes gemini-3.8-flash and gemini-3.5-flash-lite. Cached analysis can be reused; auto-analyze is supported while loading a track.

Search history and library search

/history browses saved songs/analyses with filtering, quick load, tag chips, artist links, and delete actions. Band/song pickers and global search use the same catalog. A short-lived, mutation-aware cache avoids repeating the distinct-artist query.

Search records are unique by normalized artist and title.

Artist intelligence and scene discovery

/artist combines the local catalog with concurrent Setlist.fm, Last.fm, TheAudioDB, and Spotify lookups. Profiles can show origin, formation year, biography, artwork, related artists, saved songs, and library presence. Regional concert filters pass a selected state to Setlist.fm.

Artist views also support tour/setlist exploration, average setlists by year, and one-click analysis of catalog tracks.

Concert and tour intelligence

Setlist.fm supplies concert history, average setlists by year, play frequency, stage ordering, venue/city/state details, and touring co-performers. Recent tours expose co-headliners, tour mates, openers, and festival performers. Setlist tracks can be cross-referenced with saved analyses.

Track and artist enrichment

Last.fm provides track tags, artist tags, listeners, play count, top tracks, and similar artists. TheAudioDB can supply album, genre/style, mood/theme, tempo, key, time signature, duration, video links, artwork, and audio attributes. Enrichment is cached and reused by profiles, recommendations, and playlist filters.

Spotify listening dashboard

Each signed-in user can connect Spotify through OAuth. The dashboard syncs recently played songs, shows current playback, and summarizes hour/day patterns, frequently played artists, release eras, and listening personas. Tracks can jump into lyrics analysis.

Credentials/history are stored per email in spotify_tokens and spotify_history; artist profile cache may also include Spotify data.

Playlist generation

/playlists generates lists from analyzed songs, artist catalogs, Last.fm tags, TheAudioDB attributes, Spotify listening, or Setlist.fm tour data. Filters include artists, tags, mood, year, order, deep cuts, limits, and a custom name.

  • All analyzed: every catalog track with saved analysis.
  • Artist or multi-artist: one artist catalog or a blend.
  • Genre/mood/audio: use community tags and track attributes.
  • Spotify rotation: combine saved analyses with top/recent listening.
  • Average setlist: concert-derived order and play counts.

Multi-artist blend engines

Catalogs are fetched concurrently, preferring Spotify, then Last.fm, then the local analyzed/history catalog. Tracks are enriched from saved lyrics, analysis, tags, and audio details.

  • Alternating: round-robin tracks across artists.
  • Thematic Gemini: find cross-artist themes, sequence a narrative, and explain each connection.
  • Heuristic fallback: use tags, lyrics/analysis keywords, mood, tempo, energy, valence, danceability, and acousticness.

Thematic results are cached in thematic_curation_cache.

Saved playlists and exports

Playlist metadata is stored in playlists; ordered track snapshots go in playlist_items. Users can reload/delete and export to Spotify, M3U, Apple Music-compatible playlist text, or CSV, or copy a tracklist. Successful Spotify exports save the returned playlist ID and URL. Cover art uses Gemini image generation with a Pillow procedural fallback.

Ratings and recommendations

Ratings are per user email and upserted by normalized artist. The scale is 0 unknown, 1 dislike, 2 okay, 3 like, 4 really enjoy, 5 favorite. Ratings can be edited, filtered, searched, sorted, and deleted.

Recommendations query cached or live Last.fm similar artists. Rating weights: 5=3.5, 4=2.5, 3=1.2, 2=0.3; dislikes are excluded as seeds and matching candidates suppressed. Candidates related to multiple liked seeds get a synergy boost and rationale. With no positive ratings, analyzed library artists can seed suggestions.

Rapid discovery and catalog curation

The discovery view presents one artist at a time and saves asynchronously. Keys 0–5 rate, Space/→ advances, and ← goes back. Positive ratings can discover related artists in the background. Other views cover analyzed artists and recommendations, with filtering, sorting, direct actions, and in-place ratings.

Custom prompt templates

The prompts page adds analysis templates, stored in prompts.json or PROMPTS_FILE_PATH, not in the database. Prompt configuration is separate from each song's persisted analysis.

Concurrent aggregation and PWA assets

Independent provider lookups use thread pools where implemented; failures are isolated so one unavailable source need not block others or the local catalog. The server exposes a manifest/icons and a public health endpoint; application pages and APIs require a session.

External services

Integrations and roles

Provider data is best-effort and cached. Optional credentials enable specific features; manual lyrics entry and the local library remain available independently.

Content and analysis

Genius resolves songs and provides lyric pages; LRCLIB is the open lyrics fallback; Google Gemini generates analysis and thematic curation. Genius accepts an access token or OAuth setup; Gemini needs an API key.

Music intelligence

Last.fm supplies tags/artist relations; TheAudioDB supplies track/artist facts; Setlist.fm supplies concert/setlist data; Spotify supplies user listening, artist tracks, and playlist export. Spotify user features require OAuth credentials and authorization.

Credentials can be provided by environment variables or the local secrets module. Never put secret values into this reference.

Identity and runtime

Access and operations

One request handler serves local and deployed use, with authenticated sessions around protected application routes.

Google sign-in and roles

Google OAuth supplies the account email. Access is restricted to provisioned users; initialization seeds the primary administrator. Administrators can grant access, set roles, suspend/reactivate, or remove users. Safeguards protect the primary superadmin.

Sessions and route protection

Authentication creates a random session ID with an expiry (the helper defaults to 30 days). Page requests redirect unauthenticated users to /login; APIs return 401. Admin pages require admin status. /healthz and static assets are public.

Database selection

Target precedence: explicit function target, DATABASE_URL, NEON_DATABASE_URL, DATABASE_PATH, local secrets URL, then project calling_hours.db. PostgreSQL uses psycopg2; SQLite enables WAL and foreign keys per connection.

Local and cloud runtime

Install requirements.txt, configure provider credentials, and run calling_hours.py. Docker and Cloud Run deployment are supported. In production, supply credentials through environment variables or a secret manager; exclude populated local secrets from images.

Ownership caveat: playlist rows have no user_email owner field; playlists and the song/artist catalog are shared within the configured database. Spotify state and ratings use email keys, but those fields are not foreign keys to users.

Storage notes and schema boundaries

Backend differences

  • Primary keys use SQLite auto-increment integers or PostgreSQL SERIAL.
  • User flags use PostgreSQL BOOLEAN and SQLite integer 0/1.
  • Artist listeners/playcount use PostgreSQL BIGINT and SQLite INTEGER.
  • PostgreSQL migrations use ADD COLUMN IF NOT EXISTS; SQLite checks PRAGMA table_info.
  • SQLite enables FK checks per connection. Only playlist parent-to-items is an actual FK.

Serialized data

Portable TEXT columns store JSON-like provider values and criteria: tags, audio details, artist payloads, playlist criteria, and curation output. Formatters decode valid JSON and use an empty list/object or None when data is missing or malformed.

Not database tables: prompt templates live in prompts.json; secrets/configuration come from environment or the local secrets module; external providers remain the source for uncached facts. This dictionary covers all ten tables in the schema initializer and its migrations.
